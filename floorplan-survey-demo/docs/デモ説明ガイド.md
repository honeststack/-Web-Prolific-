依頼者にデモを見せて説明する方のための資料です。

## 1. 依頼者に見せる前の準備

1. README の手順でNetlifyに配置します。
2. 管理画面の「動作試験」タブを開き、同時参加20人・回答6問で試験を実行します。**これが本番環境での最初の同時アクセス確認です。** 結果を確認してください（→ 6章）。
3. 「調査設定」タブの全削除で試験データを消します。
4. 概要タブの「模擬参加者を追加」を2〜3回押し、グラフにデータがある状態にします。
5. 依頼者に操作してもらう場合は、`ADMIN_PASSWORD` を設定するか判断します。未設定なら依頼者はログイン不要ですが、URLを知る人は誰でもデータを削除できます。

## 3. 依頼文で説明を求められている2つの論点

### 論点1：回答数の均等化と条件別の出題比率の両立

**画面：** 管理画面 → シミュレーション

**説明：**

> 開始時に問題をまとめて確保せず、1問ごとに、その時点で回答数が最も少ない問題から選びます。参加者ごとに a〜g の出題枠（N=40 なら 8/4/4/8/4/4/8）を先に決め、その条件の中で最も回答の少ない問題を割り当てます。
>
> その条件の問題が全体の最少回答数より一定以上多くなると、依頼文の優先順位どおり、均等化を優先して別の条件から出題します。別の条件から選ぶときも、その参加者にまだ枠が残っている条件を優先するため、比率はできるだけ保たれます。

**見せる数値**（参加者1,000人、離脱率20%、同時50人、乱数を変えて3回実行）

| 問題データ | 指標 | 本システム | 単純ランダム |
|---|---|---|---|
| 比率どおり | 回答数の最大−最小 | **1〜2** | 25〜27 |
| 比率どおり | 回答が最も少ない問題の回答数 | **11〜12** | 0〜2 |
| 比率どおり | 完走者の条件配分が計画どおりの割合 | **100%** | 100% |
| 偏りあり | 回答数の最大−最小 | **2** | 64〜66 |
| 偏りあり | 完走者の条件配分が計画どおりの割合 | 0.5〜0.9% | 99.6〜100% |

**読み方：**
- 問題データ自体が 2:1:1:2:1:1:2（600/300/300/600/300/300/600組）なら、**均等化と条件比率は完全に両立します。**
- 比率と合わないデータでは、問題ごとの回答数を揃える限り比率は守れません。これは方式の限界ではなく算数上の制約です。出題比率はデータの構成に近づきます。依頼文の「均等化を優先」に沿った結果です。
- **依頼者への質問：** 実データの条件別の問題数を教えてもらえれば、どちらの状況か確定します。提案の説得力が増す質問です。

### 論点2：離脱後の再割り当て

**画面：** 解説パネル「戻るを試す」、調査設定の「離脱の検知と再割り当て」

**説明：**

> 1問ずつ割り当てるため、離脱者が抱えたまま残る問題は最大1問です。未回答の問題をまとめて解放する処理そのものがほぼ不要になります。

| 離脱の種類 | 検知方法 | 解放のタイミング（初期値） |
|---|---|---|
| ブラウザの「戻る」 | ブラウザのイベント | **即時** |
| タブを閉じる | ページ終了時の通知 | 15秒後（再読み込みと区別するため） |
| 通信断・強制終了 | 30秒ごとの定期通信の途絶 | 120秒後 |
| 開いたまま放置 | 1問の経過時間 | 900秒後 |

- 「即時」と言えるのは「戻る」だけです。タブを閉じる操作と再読み込みは、ブラウザからは区別できないため猶予を設けています。ここは正直に説明してください。
- 依頼文に「タイムアウトは相談して決定」とあるため、3つの時間はすべて管理画面で変更できます。
- 解放された問題は、次に割り当てを行う時点で他の参加者に渡ります。
- 解放後に元の参加者の回答が届いた場合も、データを失わないよう保存します（`late_after_release=1`）。その問題の回答数が1だけ増えることがあります。

## 4. その他の要点

| 依頼内容 | 実現方法 | デモで示す場所 |
|---|---|---|
| 同時アクセスで競合しない | 割り当ての集計は条件付き書き込みで更新し、他者と競合したら計算し直します | 動作試験 |
| 通信エラーでも失わない | 回答を先に保存してから集計します。再送しても二重に数えません。保存を確認するまで次へ進みません | テストで確認済み（実演するならブラウザをオフラインに） |
| 回答時間の定義 | 3枚の描画完了から確定までを計測。3枚が揃うまで画像を出さず回答もできません | 本試行 |
| 同じ問題を重複させない | 参加者ごとの出題済みリストをサーバーで管理します | 動作試験の「重複出題」 |
| 全問回答者の再回答防止 | Prolific IDをキーにサーバーで拒否します。Study IDが変わっても防げます | 完了後に同じURLを開き直す |
| 欠損・破損の検出 | PNGをCRC検証と展開まで確認し、同じIDの画像の一致も照合します | データ取込・画像 |
| 保存データとCSVの一致 | 保存データから問題別回答数を数え直して照合します | 動作試験の「データ整合性チェック」 |

## 7. 想定問答

**Q. 月額費用はいくらですか？**
Netlifyの料金プランとBlobs・Functionsの利用枠で決まります。画像は1枚約1KB（スライド内の見本とダミーでの実測）で容量は小さく済みそうです。**最新の料金は未確認なので、提案前にNetlifyの公式情報で確認してください。**

**Q. なぜ既存の実験フレームワーク（jsPsychなど）を使わないのですか？**
問題の割り当てをサーバーで集中管理する必要があるためです。画面側を既存フレームワークにすることも可能ですが、難所は割り当てと保存にあります。

**Q. 参加者が開発者ツールで不正をできますか？**
理解度確認と注意力確認の正解はサーバーだけが持ちます（`DEMO_MODE=false` ではブラウザに送りません。デモの解説パネルに正解が出るのはデモ機能です）。ただし画像のURLには問題IDが含まれるため、抽出条件は技術的に読み取れます。必要ならURLを匿名化できます。

**Q. Nを途中で変えられますか？**
参加者データがある間はサーバーが拒否します。依頼文の「調査開始前に設定」に合わせた動作です。

**Q. デモのデータは本物ですか？**
間取り図と問題はすべて自動生成のダミーです。「模擬参加者」もダミーですが、実際の割り当て処理を通っており、CSVでは `source=simulated` と区別されます。

## 8. CSVの構成

| ファイル | 単位 | 内容 |
|---|---|---|
| 回答データ | 1回答1行 | 全画面の回答。`screen_id`・`question_id`・`row_type` で区別。本試行は `triplet_id`、参加者は `prolific_pid` で紐付け |
| 参加者 | 1人1行 | 完了状況、注意力の合否、アクセス回数、イベント履歴 |
| 問題別 | 1問1行 | 回答数、回答中の数、画像エラー数、出題停止の状態 |

`row_type` は `consent`、`comprehension`、`practice`、`main`、`attention`、`post`、`demographic` のいずれかです。分析では `row_type=main` かつ `source=prolific` を使います。列構成は依頼者との相談事項です。
